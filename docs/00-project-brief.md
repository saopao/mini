# 项目简报

## 项目名称

开店避坑助手

## 输入来源

## 一句话目标

为准备开店和开业早期的小店经营者提供一个跨端小程序，用最少输入完成开店测算、经营目标拆解、日常记账、看板追踪和策略推演。

## 产品定位

本产品不是通用记账软件，也不是重型门店 SaaS，而是面向新手店主的轻量经营决策工具。

V1 聚焦以下闭环：

1. 选择行业模板，降低首次建模成本。
2. 输入关键经营参数，生成开店测算报告。
3. 把回本目标拆成月流水、日流水、日单量。
4. 用日看板判断今天是否达标。
5. 用快速记账回填真实收入和支出。
6. 用实验室调整关键变量，比较方案变化。

## 目标用户

| 用户 | 阶段 | 核心问题 | V1 对应能力 |
|---|---|---|---|
| 准备开首店的人 | 开店前 | 这个店每天要卖多少才不亏、多久能回本 | 行业选择、开店测算、经营报告 |
| 开业 0-180 天的新手老板 | 开业早期 | 今天、本周、本月有没有跑赢目标、实际利润如何 | 看板、快速记账、周期趋势 |
| 低人手小店经营者 | 日常经营 | 没时间用复杂系统，但需要快速判断 | 10 秒记账、目标完成率、风险提醒 |

## V1 范围

必须包含：

- 欢迎页
- 行业选择页
- 开店测算页
- 经营报告页
- 看板页
- 快速记账页
- 实验室页
- 我的页
- 本地数据持久化
- 核心公式计算
- 风险标签与提示
- 异常输入处理
- 免责声明

暂不包含：

- 多店铺管理
- 员工权限
- 库存、进销存、收银、CRM
- 自动对账
- 发票和税务模块
- 会员、社区、课程
- 微信支付商业化闭环
- 强制登录和强制云同步

可预留但不在 V1 强依赖：

- 可选登录
- 云同步
- 数据导出
- 分享报告图
- 周复盘
- 付费模板包
- 顾问协同版本

## 首发端与跨端原则

首发体验以微信小程序为基准，因为设计稿、用户场景和报告均以微信生态为主要承接环境。

后续实现应保留跨端小程序扩展能力，至少在文档、状态、样式和数据层面避免绑定单一平台能力。若后续选择 Taro、uni-app 或原生小程序，需要先补充技术选型记录。

跨端约束：

- 页面信息密度以 375px 宽移动端为最低基准。
- 所有数据计算逻辑应平台无关。
- 存储层应通过 repository 或 service 抽象，避免业务页面直接依赖具体平台 API。
- 平台能力如分享、订阅消息、登录、支付必须有降级方案。
- 不使用只有单一平台支持且无法降级的核心交互。

## 成功标准

| 指标 | V1 验收目标 |
|---|---|
| 首次建模 | 用户 3 分钟内可从欢迎页到经营报告页 |
| 报告理解 | 用户能看懂每天至少需要多少流水和多少单 |
| 看板判断 | 打开看板 10 秒内知道今天是否达标 |
| 记账效率 | 单笔收入或支出录入不超过 10 秒 |
| 实验室推演 | 修改任一核心变量后能看到前后对比 |
| 数据一致性 | 修改模型或删除记录后，报告、看板、实验室同步重算 |
| 空状态 | 无模型、无记录、少量记录时都有明确引导 |

## 关键假设

- 用户愿意为“少踩坑、看清回本线”投入 3 分钟完成首次测算。
- 用户不愿意做复杂会计记账，但可以接受每天 30-60 秒记录核心经营数据。
- 行业模板的价值在于降低输入门槛，不是精确预测未来。
- V1 先验证“连续使用”和“经营判断价值”，再验证重商业化。

## 未确认事项

- 首发行业优先级。
- 首发城市或城市层级。
- 是否启用登录。
- 是否启用云同步。
- 是否接入 AI 面向用户输出经营建议。
- 是否上线付费模板或订阅。
- 小程序主体类型与备案计划。

在这些事项未确认前，后续实现默认采用匿名、本地优先、单店铺、免费基础功能方案。
